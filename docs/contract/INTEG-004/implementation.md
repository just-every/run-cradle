# Google record sync implementation

This preparation adds a Google subset; it does not change INTEG-004 acceptance or status.

The calendar panel lives in a record's detail and in its calendar view. A native base owner or creator chooses a date field, optional same-type end field, scalar title and further scalar fields, their own Google connection, and an owned calendar matching that connection's account ID. The panel warns that calendar readers see those values. Saving captures a definition version and an explicit audited approval naming the calendar ID. The existing Calendar scope mismatch guard remains in both repair and record adapters.

Scopes are `https://www.googleapis.com/auth/calendar.events.owned` and `https://www.googleapis.com/auth/calendar.calendarlist.readonly`. The read-only existing `connection.sync` job lists owned calendars and marked events. It never performs a calendar write. Production consent has not been exercised; tests use synthetic credentials and a network-edge Google implementation only.

Every create, move and cancel goes through the existing execution service under class `record.calendar.sync`. The key is derived from definition, record and event generation; create derives the Google event ID from the key. The request is sealed, policy is checked again at dispatch, ETags fence moves/deletes, and provider readback settles the event binding with the attempt receipt. An unknown acknowledgement has no replay capability and is reconciled by readback. The existing definite-refusal retry path retains the same sealed input and key. Readback remains subject to current read authority.

Ordinary admitted record commands capture durable pending changes through the existing record automation context. The trigger recognizes create, patch, delete, restore, undo and bulk commit; an import's inert admission does not set that context. A unique definition/record/command tuple prevents duplicate fan-out. Automatic preparation admits at most ten calendar attempts in sixty seconds and pauses a record behind its unsettled attempt or review. Source version guards prevent an obsolete body being dispatched after a newer record write.

Definitions currently retain the approving native actor and require that original session to remain current. This is a conservative session-bound subset, not AUTO-USER-001's independent delegated credential lifetime. The panel shows stopped after role, connection, class, date-read or original-session loss. Saving again captures the current approving session. A field no longer readable is omitted from a newly prepared event; an already prepared body with a now-hidden field is stopped before dispatch.

Google private properties identify the definition and record and bind the last written body hash. A read job compares provider ETags to the last confirmed write. Move, retitle and deletion observations open review and fence that event. Apply uses the ordinary policy-checked record writer and admission, so ordinary record automation capture still occurs. Restore of an existing calendar event is an explicit move effect using the observed ETag. A deleted provider event can currently only be applied as a cleared date; recreating it then requires an explicit record date and sync. Restoring a deleted provider event directly is a Gap.

Configuration versions, bindings and pending changes are additive migration `9051_record_calendar_sync.sql`. No seeded rows or applied migration are replaced. Installation archives exclude the ephemeral owned-calendar catalogue and provider credentials, disable definitions, replace retained actor context with an empty object and complete pending changes. Restoring and reauthoring under a different owner is not yet exercised.

The existing `tests/ui-records-calendar.mjs` registration calls `tests/helpers/record-calendar-journey.mjs`; no registration is added. The helper drives the emitted Worker, real native session and record/connection/definition routes with Google faked only at the network. It captures configured/review/resolved screens at 1440 and 390 and checks serious axe findings and horizontal overflow. Tests and screenshots are evidence only when the parent records a passing exact candidate run.

Gaps pending proof or implementation: Outlook (`Calendars.ReadWrite`, Graph transaction ID and private-property readback); real provider consent; delegated definition lifetime; direct restore of externally deleted events; resolving a review by another authorized date-field writer; import-no-effect, bulk-pacing, definite-429 same-request and author-demotion public probes; populated upgrade and installation archive restoration. The parent owns final acceptance mapping and status.
