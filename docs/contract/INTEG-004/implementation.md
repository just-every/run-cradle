# Record calendar sync

A native base owner or creator chooses a date field, an optional end field of the same type, a scalar title, further scalar fields, their own Google Calendar or Outlook connection, and an owned calendar matching that connection's account ID. The record panel states that calendar readers see those values. A date field has one sync definition. Saving versions the definition and records an explicit approval naming its calendar ID.

Google consent uses `https://www.googleapis.com/auth/calendar.events.owned` and `https://www.googleapis.com/auth/calendar.calendarlist.readonly`. Outlook uses Microsoft Graph with `Calendars.ReadWrite` and `offline_access`. The read-only `connection.sync` job lists owned calendars and marked events; it never writes an event. Shared-with-me Outlook calendars are excluded. A base owner or creator can configure and consent to their own calendar connections, without acquiring authority over anyone else's connection. Real provider consent remains NOT RUN.

The definition's approval has an independent scoped credential, expires within 30 days, and cannot be recovered as a bearer secret. Revoking the native session that approved it does not revoke this bounded approval. Saving renews it and retires the prior version's credential. The author's current account, authentication epoch, base owner or creator role, row policy and field policy are rechecked before effects start. A removed role, revoked connection, missing calendar class, unreadable date or expired approval stops sync. A newly prepared event omits fields the author can no longer read. Older session-bound definitions require explicit renewal before further effects.

Every create, move and cancel uses execution class `record.calendar.sync`. Its key derives from the definition, record and event generation. Google derives the event ID from that key. Graph sends the key as `transactionId` and a named private single-value extended property; readback finds the event by that property and validates the definition, record, body hash and typed dates. Google ETags and Graph change keys fence moves and deletes. Provider-confirmed readback settles the event binding with the attempt receipt. An unknown acknowledgement is reconciled without resend; a definite 429 follows the existing scheduled retry with the same sealed input and key.

Ordinary admitted create, patch, delete, restore, undo and bulk commands capture durable changes. Imports do not enter that context. Each definition, record and command has one capture. Automatic preparation admits at most ten calendar attempts per minute and leaves later changes durably pending. A record waits behind its unsettled attempt or open review. Cancellation of an already-bound event can inspect a trashed record through server-owned custody; current account, role, row and field policy still apply. Ordinary record reads cannot request that custody. Restoring the record creates a new event generation. Source-version guards stop an obsolete body after a newer record write.

Marked-event reads compare the provider's current ETag or change key with the last confirmed write. External moves, retitles and deletions open review without editing the record. Any person with current write authority on the date fields can resolve it. Apply is an ordinary policy-checked record write. Restore is an explicitly authorized effect under both the clicking person's current date-write authority and the definition author's current scope. An existing event moves using the observed version; a deleted event is recreated in a new generation. A date writer needs no export permission of their own: the author-approved export projection supplies the event, and hidden values remain unavailable through that writer's record and execution-detail doors. A reader cannot resolve a review. Other writers can see and resolve accessible reviews but cannot edit the author's definition or manage their connection.

Migration `9050_record_calendar_sync.sql` is additive. The populated-upgrade helper applies that shipped SQL around existing records, schema and sealed consent, then the public calendar journey configures and dispatches effects. No applied migration is replaced.

Installation archives exclude calendar catalogues, provider credentials and approval credentials, disable definitions, clear retained actor context and complete pending changes. Explicit native admission of the fresh restored owner transfers only the archived owner's calendar setup custody; personal file-store connections do not transfer. The new owner must reconnect the calendar and save a new approval before effects can resume.
