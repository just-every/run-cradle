# Managed admission

The intended public project is `just-every/cradle`. Publication remains with the
owner. Ordinary
local installation and owner-account deployment remain available through the
README. Managed installation uses the same Base operator-auth credentials and
Cradle owner policy.

## Build the source delivery

`packaging.json` is the source policy. Its `setup.manifestFile` selects the root
`rer-setup.json`. `scripts/build-delivery-artifact.mjs` calls the vendored Base
producer; it packages the actual emitted Worker modules, client assets, resource
declarations and all four ordered migration groups. It never provisions resources
or deploys. The generated `rer-project.json` records the SHA-256 digest of the
canonical setup bytes. Preserve every already-applied migration byte.

The managed workflow is dispatch-only and pins the trusted reusable workflow to
`bf7a25abb44bec1457a7bc738ff63921d90fb52e`. It declares full verification. The
project profile runs its source-owned setup, build, verify and artifact operations.
The project operations use `node scripts/rer.mjs install`, `build`, and `verify`.
The rer CLI selects the declared Node runtime. Browser preparation is explicit in
the producer setup command; artifact packaging uses the actual delivery producer.

To prepare the artifact locally with the pinned tools, run:

```sh
node scripts/rer.mjs install
node scripts/rer.mjs build
pnpm delivery:artifact
```

The output is `delivery-artifact/rer-worker-artifact.json` plus its referenced
payloads. They form one artifact; retain the whole directory. The source workflow
and descriptor are generated by Base's producer from the same policy and setup
bytes. The producer's portable export changes only its documented setup-schema
import and URL roots. Edition origins retain the original Base source for review.
The exported policy snapshot is omitted because the thin caller reads the root
`packaging.json` directly. Copied Base tests are excluded.

## Admit the owner

The manifest declares signed owner claim at `/auth/owner-claim`. `SETUP_TOKEN` is
a required, generated, hidden secret. The owner receives a short-lived signed
claim through the management service, and never receives that setup secret.
Cradle calls Base's owner-claim handler with the configured owner email and these
platform-supplied public verification bindings:

| Binding | Purpose |
| --- | --- |
| `RER_OWNER_CLAIM_ISSUER` | Exact management issuer |
| `RER_OWNER_CLAIM_INSTALLATION_ID` | Installation audience |
| `RER_OWNER_CLAIM_APP_ORIGIN` | Exact application origin, matching `APP_ORIGIN` |
| `RER_OWNER_CLAIM_PUBLIC_KEYS` | ES256 public verification key ring |

Only a valid claim for this owner, installation, issuer and application origin
can atomically establish the first Base owner and session. Existing operators or
the consumed claim ledger permanently prevent another first-owner claim. Preserve
that ledger during recovery. Subsequent sign-in, invitations and revocation use
the ordinary Base auth and Cradle's native authority projection. Local setup uses
its private generated bootstrap secret and the development mail outbox. The same
manifest names `MAIL_PROVIDER`, `MAIL_FROM` and `MAIL_PROVIDER_API_KEY` for managed
hosting. Choose SendGrid or Resend and a verified sender for a hosted install. The
local installer saves entered hosting settings in private `data/hosting-mail.json`
and keeps its temporary app on development delivery; the hosting phase receives
only the explicitly selected hosted provider settings. This file is local private configuration; preserve or deliberately remove it
with your local installation state.

## Edit as the current owner

Configure `RER_MANAGEMENT_ORIGIN` and `RER_INSTALLATION_ID`; set
`RER_EDITOR_ENABLED=false` to disable the mount. `/api/editor/config` admits only
the current active Base owner with Cradle's active initial-owner principal and
current native session. Grants contain three public configuration fields and a
short expiry; they are private and non-cacheable. Non-owners and revoked sessions
receive no grant. No management credential enters the application browser.

The native owner shell owns the copied editor controller. Native session failures
and sign-out remove its private overlay; focus and bounded renewal recheck server
authority. A silent server change is observed within the short grant lease. A
configuration failure is shown in the owner's existing error surface. An equivalent
grant renewal preserves the open editor and unsent draft; changed, rejected or
expired configuration removes the prior mount under the shared controller contract.
The same compiled edit runtime is installed before the owner gate for every
visitor. Every actual route leaf, including sign-in and errors, marks hydration
ready. Owner teardown preserves published edits.

Application HTML retains its existing CSP and permits the exact management origin
in `frame-src`. The management `/editor` response must independently allow the
registered application origin in its HTTP `frame-ancestors` header. A query
`parentOrigin` is never registration. The reviewed platform source implements this
policy; the native browser tests use a labeled network fixture for allow/deny
framing and protocol negotiation. Those tests do not prove deployed management
headers.

## Owner acceptance

Stage and production installs, hosted origin registration, public publishing and
tags belong to the owner. Before hosted acceptance, the platform owner must
provision the signing-key ring through the trusted controller and enable the
appropriate owner-claim policy. Platform main's
`docs/runbooks/owner-claim-stage-key-provisioning-prerequisite.md` records the open
stage controller prerequisite. Then install this exact source release into fresh
resources, prove signed owner admission and real sign-in, and inspect the actual
management editor header and owner mount at 1440 and 390. No stage or production
deployment is performed by the source build.
