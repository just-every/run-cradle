The records builder is the lead product. Launch readiness is an included template with every retained clause still binding; repairs are optional navigation and their full outcome remains separately gated. The October shell has one Home, grouped navigation, literal-localhost development access and a themed 404. See the [identity transition](docs/contract-transition.md#records-first-identity--6-october-2026).

Foundation acceptance requires frozen installation and default `pnpm verify` (records and all 11 launch files included; 10 launch suites plus their helper), preservation of the approved shell composition, mobile/desktop shell evidence, accepted Base operator-auth/mail/deploy adoption, and an exact disposable-install receipt with received magic-link owner sign-in and complete resource teardown. Readiness notification delivery remains a separate workflow gate. Docker authoring is an explicit `pnpm verify:authoring` profile. Local checks do not accept external providers, CI, bootstrap or deployment; HANDOVER.md records each separately.

The wider records and workflow gates below remain obligations and are not satisfied merely by changing product identity.

## Manual records release profile

The foundation release adds an owner-built CRM without AI: Companies, Contacts
and Deals, typed fields, links and a lookup. Every schema change requires an
impact preview and guarded adoption; stale data, schema or authority rejects the
prepared change. Grid sorting, filtering and grouping, saved views, kanban and
forms have desktop and phone browser journeys with no page overflow and zero
serious or critical automated accessibility findings. Per-view CSV is checked
against a fresh table, including human select labels, linked records, computed
lookups and nullable values. Customer relationships, project tracker and launch
readiness are included templates.

These repeatable acceptance checks run in `pnpm verify`. Rollup and formula
authoring, rare field types, gallery, charts, comments, bulk editing, record
history and attachments are outside this bounded profile. The broader planned
requirements below remain separate. Hosted owner sign-in, resource teardown, CI
and publication inspection each require their own exact-candidate receipt.
