## Legacy atomic transition refinement (before product edits)
The unchanged journey also compares retained table contents across late failed erasures. Therefore legacy snapshots cannot be compacted destructively during erasure preparation. Instead, establish schema-only retirement triggers for exact metadata-owned terminal copies. Each trigger is attached to deletion of its owning rer_portability_jobs row and clears those copy tables inside the SAME native erasure batch. Preparation changes no retained data, authority, receipt or checkpoint. Inventory + trigger-definition fences and final empty-copy predicates prove the atomic wipe. Unknown/orphan copies retain the existing transactional DROP path. Empty tables/triggers are then collected after the durable erasure checkpoint, when they contain no bytes and no job can address them; failure there cannot resurrect content or create partial data loss. Final completion and retry reconcile this physical schema cleanup. New completed exports compact normally after full archive verification, so ordinary retention no longer keeps per-table copies. This is an edition schema/custody integration using ordinary SQLite transactional triggers; it neither increases a budget nor splits the native erasure into batches. No applied SQL migration needs changing and no new persistent product data table is needed.
