# Runtime probe

PROBE CAMP-009 1: enabled owner-authored campaign.updated and risk.updated add-activity definitions saved through launch.automation.save; their committed events admitted through cradle.launch.events.v1 while execution delivery is held -> public history has one Queued run for the campaign and one for its risk child, each with one Pending action and one pending execution outbox row. launch.campaign.archive with a freshly read version -> both histories are Cancelled, both execution rows are cancelled and no action has started. Repeated retained execution messages, two scheduled ticks and a new Worker instance -> neither distinguishable activity description appears; unrelated queued history becomes Succeeded with one Complete action and exactly one public activity description.

This probe is the existing emitted Worker registration in ./tests/launch-installed-event-control.mjs, extended by verifyPublicQueuedCampaignArchive in ./tests/helpers/launch-queued-campaign-archive.mjs. The helper uses public HTTP commands, record reads, run history and campaign activity, and real queue and schedule doors. Supplemental D1 reads only correlate committed event and execution identities; no run, action or outbox rows are fabricated or rewritten by this helper. Automatic execution delivery is held by the existing test runtime's automaticQueues=false option.

The initial local attempt found a test readback error: it looked for the database's message field instead of the public activity description field. The unrelated positive control failed with 0 != 1. Corrected readbacks now use description for both forbidden effects and the successful control. No production behavior was changed and no existing assertion was removed or weakened.
